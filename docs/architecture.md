## PBM のデータモデル

PBM トークンは「JPYC を担保にロックされた、Purpose 付きの請求権」として表現する。

```
PBMToken {
  id              : UUID
  program_id      : 助成金プログラムへの参照
  holder_pid      : 住民の擬似 ID (HMAC(maina_id))
  jpyc_locked     : ロック済み JPYC 数量 (= 助成金枠)
  purpose         : 対象 JAN リスト / 助成率 / 上限 / 期限 / 地域 ...
  status          : ISSUED / PARTIALLY_USED / EXHAUSTED / EXPIRED / REVOKED
  issued_at       : 発行時刻
  expires_at      : 失効時刻
}
```

`purpose` は `Program` 側で管理し、PBM トークンは program_id 経由で参照する。
これにより、東京都はプログラム単位で条件を一括変更/失効できる。

## Eligibility (受給資格) の判定

`EligibilityService.check(citizen, program) -> (ok: bool, reason: str)` は
マイナンバーカードから取得した 4 情報を入力に取り、プログラム要件と照合する。

| 4 情報   | 主な使い方                                                |
|----------|-----------------------------------------------------------|
| 氏名     | KYC ログのみ。判定には用いない (差別防止)                  |
| 住所     | 都内 23 区/市町村のホワイトリストと照合                    |
| 生年月日 | 年齢区分 (例: 65 歳以上 / 18 歳未満の子の保護者) を計算    |
| 性別     | 妊婦健診クーポンなど特定プログラムでのみ利用 (任意)        |

## 購入時のシーケンス

```
住民スマホ           加盟店 POS           Backend                   JPYC エスクロー
  │  QR 提示  ──────► │                                                  │
  │                   │  POST /purchase (JAN, qty, citizen_pid, store)   │
  │                   │ ───────────────► │                                │
  │                   │                  │ 1) JAN → 商品マスタ            │
  │                   │                  │ 2) 適用可能な PBM 検索         │
  │                   │                  │ 3) PBMService.spend()          │
  │                   │                  │   ├ purpose 検証              │
  │                   │                  │   ├ 助成額算出                │
  │                   │                  │   └ JPYC アンラップ ─────────► │ store wallet++
  │                   │                  │ 4) 自己負担分は通常 JPYC で清算│
  │                   │                  │ 5) EBPM ログ書き込み           │
  │                   │ ◄─────────────── │  201 (subsidy, citizen_pay)   │
  │  レシート ◄────── │                                                  │
```

PBM の `spend` 内では以下を厳格にチェック:

1. プログラムが期間内か
2. プログラム予算残高が十分か
3. JAN が `eligible_jans` に含まれるか
4. 住民の eligibility が現在も成立しているか (引っ越し・年齢超過等)
5. 住民ごとの累計上限を超えていないか
6. 加盟店が認定店舗か

このうち 3〜6 はオンチェーン実装の場合 PBM コントラクトの `require()` に
直接対応する。

## なぜオフチェーン MVP か

- 東京都の評価ポイントは「政策効果」「実用性」「プライバシー」に置かれているため、
  まずは UX とデータ設計を素早く固める方が ROI が高い。
- PBM の状態遷移は本質的に「ロック → 検証 → アンラップ」というシンプルな
  ステートマシンで、後段で `contracts/PBM.sol` の実装に差し替えやすい。
- 本 MVP のサービス層インターフェースは `PBMService.spend` 等の単位で
  オンチェーン呼び出しに置換できるよう抽象化している。
