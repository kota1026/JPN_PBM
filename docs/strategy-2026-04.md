## 1. 憲法原則 (CP-1〜CP-6)

| ID | 原則 | 違反例 |
|----|------|--------|
| **CP-1** | **目的整合性** — 助成金トークンは政策意図 (Purpose) を逸脱して使えない | 子育て助成 JPYC が居酒屋で使える |
| **CP-2** | **プライバシー保護** — マイナンバー4情報は擬似 ID 化、個票は外部に出ず集計のみ提供 | 受給者の個別購買履歴を都が直接保持 |
| **CP-3** | **受給資格の自動執行** — 人的審査ゼロ、スマコン+公的認証で判定 | 担当窓口が個別判断で承認 |
| **CP-4** | **監査可能性 / EBPM 接続** — 全取引が検証可能、政策効果に自動蓄積 | 集計が手作業 Excel |
| **CP-5** | **不正三大リスク排除** — ① 二重支給 ② なりすまし ③ 換金転売 を技術で排除 | バウチャー転売掲示板が成立 |
| **CP-6** | **災害時可用性** — ネット/電力途絶下でも給付・支払が継続 (オフライン QR + 復旧時自動同期) | 首都直下発生で全停止 |

CP-6 は本会議で Red Team が起こし、Purpose Guardian が採択した東京独自の差別化要素。MAS / Stellar 既存事例にも欠落。

## 3. 9 フェーズ実行ログ

### PHASE 1: 課題提示 (5min)

ゴール: 12〜18 ヶ月で本番運用 1 ユースケース + 拡張可能な OSS 基盤を立ち上げる。

### PHASE 2: 提案競争 (15min)

| # | 提案者 | 提案 |
|---|--------|------|
| 1 | Purpose Guardian | **018サポート の PBM 化**。月 5,000円のうち教育関連 (書籍・学用品・通信教育・習い事) JAN/業種にのみ使える |
| 2 | CTO | **防災備蓄ローリングストック助成**。5 年保存水・非常食・防災ラジオに限定、4.5 年経過で自動再付与 |
| 3 | CSO/AML | **加盟店 KYC + Amazon-FAZZ 型エスクロー**。POS で受領確認 (JAN スキャン)→ 加盟店リリース。個別取引上限 10万円 |
| 4 | CFO | **都税還流型コミュニティバウチャー**。商店街への支出限定 PBM、加盟店受領 JPYC を都税の電子納付に充当 (税ループ) |
| 5 | CBO | **DBS×OGP 型 CDC コピー** = 区単位の食品・日用品助成。1 区 1,000 世帯× 6 店舗で 4 週間パイロット |

| 10 | Legal | **都条例サンドボックス + 資金決済法** 整合スキーム。電子決済手段としての JPYC を特定目的給付として上書き |
| 11 | Red Team | (PHASE 3 へ) |

### PHASE 3: 相互批評 (10min) — Red Team 批判

| 対象 | 攻撃シナリオ | 深刻度 |
|------|--------------|--------|
| #1 | 「教育関連 JAN」の境界が曖昧。学用品+ゲーム機の抱き合わせ販売、習い事を装ったエンタメ | 🔴 |
| #2 | 5 年保存水を 4.5 年で買い直しさせるインセンティブが弱い。倉庫で死蔵 | 🟡 |
| #3 | 小規模商店ほど KYC 負担で離脱。加盟店が 5 店だと使えない | 🟡 |
| #4 | JPYC を都税の電子納付に充当する法的根拠が現状ない | 🔴 |
| #5 | 23 区の所得格差で「区によって配られる量が違う」=政治問題化 | 🟡 |
| #6 | マイナポータル API は OAuth 同意が必要。「自動入金」は UX を間違えると個情法違反 | 🔴 |
| #7 | fork した自治体がセキュリティパッチを当てない。本家責任が不明 | 🟡 |
| #8 | JPYC 本体は ERC-20、ラッパー追加で流動性分断。JPYC 株式会社の合意必要 | 🔴 |
| #9 | 対象者数が小さく統計的有意性が出にくい | 🟢 |
| #10 | 金融庁の管轄領域に都が踏み込むと国との調整で遅延 | 🔴 |
| **横断** | **首都直下が PoC 中に発生したら? バウチャーは紙幣に勝てない (ネット停止)。フォールバック設計必須** | **🔴** |

### PHASE 4: 統合・投票 (10min)

提案を 4 クラスタに統合:
- **A: フラッグシップ** = #1, #2, #5
- **B: 横断基盤** = #6, #7, #3, #8
- **C: 法務・ファイナンス** = #4, #10
- **D: 第二弾** = #9

投票結果:

| 議題 | 結果 |
|------|------|
| 最初の本番: **#5 区別 CDC コピーを採択**、#1/#2 は Phase 2 並走 | 賛成 8 / 反対 2 / 棄権 1 → **可決** |
| 横断基盤として #6 + #7 + #3 を Day 1 から組み込む | 賛成 10 / 反対 0 / 棄権 1 → **全会一致可決** |
| #8 ERC-3643 は Phase 2 で再評価、Phase 1 は JPYC 直 + オフチェーン WL | 賛成 9 / 反対 1 / 棄権 1 → **可決** |
| #4・#10 は Legal 主導で並行リサーチのみ、Phase 3 投入 | 賛成 11 / 反対 0 → **全会一致** |
| #9 リスキリングは Phase 2 候補で待機 | 賛成 9 / 反対 2 → **可決** |

**Red Team 拒否権**: なし。ただし「災害時フォールバック」を **CP-6** として追加すべしと提案 → Purpose Guardian が即時採択。

### PHASE 5: シーケンス作成 (15min) — 18 ヶ月ロードマップ

```
Phase 1 (M+0〜M+6) — フラッグシップ パイロット
M+0  Founders' MoU: 都 × JPYC × TIS × 1 区 (江東区想定) × 商店街連合

     - 受給者 PID は HMAC 化、マイナポータル OAuth 同意取得 UI 実装
M+2  加盟店 eKYC + POS SDK 配布 (バーコード読取統合)
M+3  Closed alpha: 1 区 100 世帯 × 10 店舗 / 食品・日用品カテゴリ限定
M+4  KPI: 利用率 / 平均消化日数 / 二重支給ゼロ / 個情法インシデント 0
M+5  Public beta: 1 区 1,000 世帯 × 30 店舗 (DBS-OGP 規模到達)
M+6  パイロット結果を都議会に報告、Phase 2 予算化

Phase 2 (M+6〜M+12) — 拡張 + 第二ユースケース
M+6  23 区順次拡大、対象世帯 5万→20万
M+7  防災備蓄ローリング助成 (#2) を Closed alpha (3 区)
M+8  申請レス: マイナポータル v2 完全自動化 (#6 完成形)

M+10 PBM ラッパーの 認証コントラクト (UUPS Proxy) を audit

M+12 Phase 1+2 まとめて 都民 100 万人規模

Phase 3 (M+12〜M+18) — 制度統合 + 全国展開
M+12 #4 税ループ: 都税電子納付に JPYC 充当を試行 (法整備のうえで)

M+18 「東京都モデル」を MAS Orchid Blueprint に倣い 公開ホワイトペーパー化
```

### PHASE 7: 課題再発見 (10min)

| エージェント | 懸念 |
|--------------|------|
| Purpose Guardian | 対象 JAN リスト変更を都条例で固定化しないと CP-1 が空洞化 |
| CTO | Polygon チェーン障害時の代替 (Avalanche / Ethereum mirror)。マルチチェーン要 |
| CSO/AML | 受給者 → 加盟店 → 換金事業者 のループで現金化、JPYC 償還事業者の KYC 強度に依存 |
| CFO | JPYC 発行体倒産リスク。月次準備金監査必須 |
| CBO | 加盟店離脱: 1% cashback では商店街が動かないかも。Visa スポンサー上乗せ |
| Cost Guardian | 期限切れ JPYC 返還の利用者通知 UX、苦情コール想定 |
| Engineer | 100 万人スケールで Polygon ガス爆発、L3 / アプリチェーン検討 |
| Stablecoin Architect | JPYC ペッグが外れた時のフェイルセーフ。償還凍結条件をスマコンに埋めるか |
| Researcher | 海外事例の追従が遅い。「世界初」を取れる領域 = **CP-6 災害時フォールバック** |
| Legal | 改正資金決済法のトラベルルール強化との整合 |
| Red Team | 政治リスク: 知事交代で全部止まる。条例 + 多年度予算化で耐性 |

### PHASE 8: 機能別最終投票 (10min)

| 議題 | 結果 |
|------|------|
| チェーン選定: Polygon 単独 vs Polygon + Ethereum mirror | **両対応 6** / 単独 5 → 両対応採択 |
| eKYC: マイナ署名のみ vs マイナ署名+顔写真 | **二要素 7** / 単独 4 → 二要素採択 |
| 加盟店インセンティブ: 1% cashback vs 0.5% + 都認定マーク | **0.5%+認定 8** / 1% 3 → 後者採択 |
| 災害時フォールバック (CP-6) | **必須 11** / 任意 0 → 全会一致必須化 |
| 法務予算 | 5,000万 / 1億 / 1.5億 → **1億** 採択 |

### PHASE 9: 最終シーケンス提示 (5min)

🏛 **採択された戦略 (要約 1 ページ)**

**フラッグシップ**: 東京都 ✕ JPYC ✕ TIS による「**区別 こども・くらし応援 PBM**」 (DBS-OGP 型 CDC バウチャーの東京移植)

| 軸 | 決定事項 |
|----|----------|
| 対象 | 江東区の 0–18 歳子育て世帯 1,000 → 5万 → 20万世帯 |
| 助成 | 月 5,000円相当の食品・日用品 + 防災備蓄 PBM (018サポートの一部置換) |
| 技術 | JPYC (Polygon + Ethereum mirror) + ERC-3643 検討は Phase 2 |
| 認証 | マイナンバー署名 + 顔写真 二要素 eKYC、4 情報は HMAC PID 化 |
| 加盟店 | eKYC + POS SDK + 都認定マーク + 0.5% cashback |
| 申請 | マイナポータル v2 OAuth で完全申請レス、世帯主一括同意 |
| **災害時** | **CP-6 (オフライン QR フォールバック) 必須化** |
| OSS | `github.com/tokyo-metro/jpn-pbm` (Apache 2.0)、CSIRT は都運用 |
| 法務 | 個情法・資金決済法・都条例 3 法整合、外部弁護士 1 億円 |
| ガバナンス | 多年度予算条例化で政権交代耐性、月次準備金監査 |
