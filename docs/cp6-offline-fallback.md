# CP-6: 災害時オフラインフォールバック

> 戦略会議 #1 (2026-04-30) で **Red Team が提起**し、**Purpose Guardian が憲法原則 CP-6 として採択**した東京都独自の差別化要素。
> MAS Project Orchid / Stellar UBI 等の先行事例にも欠落しているため、**世界初**のフィールド実装を狙う。

---

## 1. 解くべき問題

| 想定 | 内容 |
|------|------|
| 首都直下地震 | 30 年内 M7 級 70%、最大避難者 300万+帰宅困難者 450万、停電・通信網寸断が数日〜2週間続く想定 |
| 平時 PBM の弱点 | オンチェーン (Polygon) と RPC が前提。停電/RPC ダウン下では PBM が **使えない** = 紙幣に劣後 |
| 都の責務 | 災害時こそ食料・水・医薬品の助成が必要 (= まさに PBM の本旨) |

→ **「PBM はネットがある間しか動かない」では 016 サポートと変わらない。** 災害時に動くことが世界水準。

---

## 2. アーキテクチャ概要

```
┌────────────────────────────── 平時 ──────────────────────────────┐
│  都 (governor)                                                  │
│   │                                                             │
│   │ 1) 月初に住民ごとの「オフライン QR」を発行・配布             │
│   │    (programId, pid, monthIndex, capJpy, expiresAt) + ECDSA  │
│   ▼                                                             │
│  住民ウォレット (アプリにキャッシュ + 紙印刷も可)                 │
└──────────────────────────────────────────────────────────────────┘
              ↓ 首都直下発生 / RPC 全断
┌────────────────────────────── 有事 ──────────────────────────────┐
│  POS (オフライン)                                                │
│   │ 2) QR を読み取り、ローカルで署名検証 + (pid,month) 内 cap 検査 │
│   │ 3) 給付実行 (紙レシート発行)、redemption をローカルキューに   │
│   ▼                                                             │
│  ローカル ledger (SQLite)                                        │
└──────────────────────────────────────────────────────────────────┘
              ↓ 通信復旧
┌────────────────────────────── 復旧後 ─────────────────────────────┐
│  都サーバ / PBMOfflineFallback コントラクト                       │
│   │ 4) POS が `redeem_batch` で集中精算                            │
│   │ 5) 都が JPYC を加盟店に payout、(pid,month) consumed を on-chain 化│
│   ▼                                                             │
│  EBPM ログ (有事用シャード) に書き戻し                            │
└──────────────────────────────────────────────────────────────────┘
```

---

## 3. CP との対応

| CP | どう守るか |
|----|------------|
| CP-1 目的整合性 | QR は (programId, pid, monthIndex) を含み、別 program に流用不可 |
| CP-2 プライバシー | pid は HMAC 化済み。QR を拾われても本人特定できない |
| CP-3 自動執行 | POS は人的判断不要。署名検証のみで給付確定 |
| CP-4 監査可能性 | redeem_batch 後に Polygon TX hash で外部監査可能 |
| CP-5 不正排除 | (1) 二重支給: (pid,monthIndex) で nonce 一意化 (2) なりすまし: 都の鍵でしか署名できない (3) 転売: pid 紐付け |
| CP-6 災害時可用性 | QR 発行から expires_at + 30 日まで有効。停電 2 週間想定をカバー |

| レイヤ | ファイル | 役割 |

## 6. Phase 1 → Phase 2 の差分予定

| Phase | 署名方式 | 鍵管理 | カバレッジ |
|-------|----------|--------|------------|
| **Phase 1 (本コミット)** | HMAC-SHA256 | `JPN_PBM_OFFLINE_SECRET` env (デモ用) | ロジック検証可能 (二重支給 / cap / 期限) |
| Phase 2 (M+11) | ECDSA (secp256k1, EIP-191) | 都の HSM | Sol の `redeemBatch` と相互運用、Polygon に書き戻し |
| Phase 3 (M+18) | + マルチシグ (都・JPYC・TIS) | M-of-N | 知事交代/緊急権限分散 |
